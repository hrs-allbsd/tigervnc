vnc-sixel implementation status and measurements
================================================
Updated: 2026-11-15 JST

Completed milestones
--------------------
1. Terminal/RFB viewer, keyboard/mouse input, cursor composition,
   resize, suspend/resume, and restoration on exit/disconnect.
2. Large framebuffer support (64M pixels) and vncviewer-compatible
   credential sources: environment and vncpasswd files.
3. Numeric performance logs and passive shared/view-only real-server
   measurement in a private Xvfb/xterm.  No remote input or screenshots.
4. Indexed fixed-palette encoding and aligned changed-region redraw.
   Identical displayed frames are skipped.  FullFrame is the fallback.
5. X11-independent terminal configure; upstream default builds preserved.
6. Fast terminal queries, XTSMGRAPHICS bounds/colors, manual geometry,
   and an eight-color fallback for limited terminals.
7. Reproducible input-to-image latency measurements, idle-aware frame
   deadlines, and configurable MaxFPS (1..60, default 10).
8. Independent sparse regions with color-run/palette cost estimation;
   SingleRect remains a fallback for diagnosis and comparison.

Paste pacing milestone (2026-11-15)
-----------------------------------
Input marks bracketed-paste boundaries and characters.  A bounded FIFO
preserves subsequent typing order while PasteRate limits pasted keys
(default 200/s, range 1..10000).  The steady-clock scheduler accrues no
burst credits during stalls.  Local commands bypass the queue; release,
focus loss, suspend and resize cancel pending keys.  Overflow cancels
unsent keys, discards the remaining paste and displays a status notice.
Already sent characters cannot be retracted.

Pasted text excludes latched modifiers and cannot complete a local
command prefix.  Typed keys queued behind paste retain their modifier
state.  The queue holds at most 8192 events, not an unbounded paste.
This limit covers the frontend key queue; TigerVNC's output stream has
its own existing limits.  Ordinary typing is not rate-limited.

- xterm tests cover modifier isolation, prefix isolation, continued RFB

RSA-AES trust and TLS milestone (2026-11-15)
------------------------------------------
Replaced unconditional RSA host-key rejection with first-contact
confirmation, SHA-256 over the RFB key blob, and a persistent complete-key
store scoped to textual host and TCP port.  KnownHosts selects the file;
StrictHostKeyChecking rejects unknown keys.  Changed keys never prompt
for replacement.  yes saves, once accepts without saving, and all other
answers reject.  X.509 verification remains unchanged and fail-closed.

The store opens without following final symlinks, checks owner/type/mode,
bounds size to 1 MiB, locks and rechecks before append, and requires sync
before accepting a saved key.  Concurrent conflicting saves cannot replace
an entry.  The default follows core::getvncdatadir(), including its legacy
fallback.  A public-key helper reproduces the displayed RFB fingerprint.
No passwords or private keys are saved in the trust store.

39 frontend tests pass, including endpoint isolation, changed-key refusal,
malformed/unsafe stores, symlinks/FIFOs, simultaneous saves and size bounds.
19 actual Xvnc/PTY cases pass: strict rejection, default/oversized-answer rejection, once,
explicit and default-path saves, strict matches, existing-directory reuse,
changed keys, unsafe/malformed stores, RA2/RA2_256/RA2ne/RA2ne_256,
anonymous TLS, trusted and untrusted X.509, and hostname mismatch.
The expected fingerprint is independently derived from the generated PEM
public key.  The harness isolates HOME/XDG directories and restores termios.
Legacy authentication and terminal negotiation regressions also pass.

Port revision 10 includes the trust store and the public-key fingerprint
helper in DOCS.  At this milestone, revoked/expired-certificate matrices,
non-TigerVNC RSA servers and an X.509 exception workflow remained pending.
No live-server key, private key or credential was recorded by these tests.

Port revision 10 validation: nice 20 build, check-plist, stage-qa and

2026-11-15: Explicit CRL freshness
---------------------------------
The old viewer accepted a correctly signed, empty CRL whose nextUpdate
was in 2001.  vncsixel now opts into CConnection::requireCurrentCRL()
for a nonempty explicit X509CRL.  CSecurityTLS::loadCurrentCRLs() reads
the PEM once, checks every parsed entry and installs the same bytes.
The maximum thisUpdate and minimum nextUpdate are checked again after
the TLS handshake.  Missing or reversed intervals also fail closed.
Other frontends retain their existing CRL loader and policy.

The private Xvnc matrix passes 41 cases: the prior 34 plus stale/future
CRLs, current bundles, and stale/future entries first or last in bundles.
Failures must include the expected expiry/future diagnostic and must
not display a framebuffer.  The 39 frontend and 273 upstream tests pass,
and normal vncviewer builds.  No live credentials or trust were used.

This does not add CRL issuer coverage, CRL signature checks beyond the
existing trusted-file handling, CRL fetching or OCSP queries.  Operators
must provide verified CA CRLs and an accurate local clock.  Third-party
server interoperability and clean poudriere jail validation remain open.
